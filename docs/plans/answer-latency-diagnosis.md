## 2. Root cause

### Established mechanism and complete wait path

For an idle automatic lane with a usable endpoint, the critical path is approximately:

`audio batching/transport + endpoint arrival + 350 ms grace + classifier complete + answer TTFT + no-op prefix hold + IPC/render`

Endpoint arrival is expected around the configured 600 ms silence threshold plus transport/provider processing, **not a measured 600 ms service guarantee**. Thus the configured acoustic-plus-assembly component is approximately **950 ms**, before either model stage. Fallback and contention are alternatives/additions as below.

The 1 ms gaps in zero-delay cases are fake-clock `setTimeout(0)` scheduling, not measured CPU cost. The 1000 ms classifier intervention changes first broadcast by exactly 1000 ms. A second boundary neither adds 1000 ms nor postpones completion. The prefix experiment proves a possible extra token-interval delay, not evidence that it commonly contributes 100 ms in production.

**Confidence:** high in the critical path and measured free-tier behavior; low in attributing the owner's live median to Haiku versus Sonnet versus STT. In the illustrative 1500/800 case, classifier time is the largest individual stage (1500/3250 ms), but those values were chosen, not observed. The owner's approximately 3 s classifier wall time includes process startup; a full 3 s inside this classifier would exceed its deadline, as the probe demonstrated. It is not a defensible live median estimate.

Ruled out for these runs: mandatory utterance-end waiting, an unconditional classifier-spacing delay, a mandatory full-answer buffer, and a multi-second local post-classifier/broadcast backlog. Existing executed policy tests also establish queue replacement, cooldown rejection, busy-lane retry, stale-candidate rejection, and reader-follow behavior. They do not rule out contention, DB stalls, renderer stalls, or different settings in the owner's installed session.

Caching is already requested on the stable system/context blocks (`claude.ts:88–94`). No cache hit/usage evidence was collected; adding the same flag again is not a fix. Lowering `maxTokens` does not inherently shorten a verdict already consisting of a few tokens. ## 4. Fix spec

### Goal

Reduce speech-end-to-first-readable-answer latency while preserving complete-turn handling, fail-closed classification, room/other addressee behavior, carried questions, cancellation, no-op suppression and reader selection. Do not optimize answer completion time as a substitute for first useful text. Establish the actual live stage medians before selecting a provider optimization.

### Placement

Extend current owners: turn timing in `services/turns/turn-assembler.ts`; classification and vendor request behavior in `services/assistant/classifier.ts` and `claude.ts`; admission in `services/meetings/assist/live-assistance.ts`; publication/cancellation in `suggestion-runner.ts`; prompt construction in `suggestion-requests.ts`/`assistant/prompts.ts`; evidence in existing assistance/run observers, `outcomes.ts`, rehearsal collection and `mock-interview/evidence.ts`/`report.ts`. Renderer receive/render acknowledgement, if needed, belongs with `useSuggestionHistory.ts` and the typed IPC contracts. No parallel provider, second automatic-answer pipeline, or new generic scheduler.

Keep files below approximately 800 lines. `live-assistance.ts` is already substantial: if speculative lifecycle logic would exceed that limit, extract a cohesive pending-answer state owner inside the existing assist home rather than appending another implementation or new top-level service. Do not combine unrelated structural-debt refactors with the latency patch.

## 5. Open questions / assumptions

- Which stage dominates the owner's live median remains unanswered without provider or session stage timings. The brief's 3 s process-inclusive classifier probe is the only supplied live observation and is not directly comparable to this in-app 2.5 s deadline.
- Installed settings and exact artifact provenance were not inspected. The baseline assumes source defaults: smart, Sonnet nudge model, Haiku classifier, default 5 s cooldown in product; the canned harness overrides cooldown to 0.
- Is a 200 ms saving worth accepting a shorter continuation window? The free run cannot establish natural-speech quality at its edge.
- What extra speculative answer spend is acceptable? Guarded speculation preserves visible fail-closed behavior but can pay for an answer on every prefilter candidate, including discarded ones; mismatch fallback can require another answer request.
- Was the owner following Latest, or reading/scrolled on an older answer? The latter intentionally prevents automatic selection. No evidence currently implicates this behavior.
- No known-good build was supplied or measured; this is an explanation of the current latency path, not proof of a release regression.
